# Campus Lost \& Found + Complaint Management System

## 1\. Problem Statement

Campus complaint handling (lost items, hostel and mess maintenance issues, and sensitive matters such as ragging) is usually managed through registers, word of mouth or scattered spreadsheets. Records get lost, nobody is accountable for resolution, and there is no safe channel for anonymous reporting of sensitive issues.

## 2\. Objectives

* Give students one place to file and track complaints across several categories.
* Give administrators tools to view, update and resolve complaints.
* Support anonymous filing in a way that is genuinely anonymous at the data level, not just hidden in the interface.
* Suggest likely matches between lost and found item reports automatically.

## 3\. Scope

* Two roles: Student and Admin.
* Four complaint categories: Lost Item, Found Item, Maintenance, Ragging.
* Complaint lifecycle: open → assigned → in\_progress → resolved → closed.

## 4\. Functional Requirements

* Users sign up and log in with a role.
* Students file complaints through a form whose fields change with the category, and view their own complaint history.
* Admins view all complaints and a per-category summary of open complaints, update complaint status (the API also supports assigning a complaint to an admin), and check lost/found matches.
* Anonymous filing is available for ragging complaints.

## 5\. System Architecture

Next.js (App Router, TypeScript) serves both the pages and the backend API routes. The routes connect to two databases:

```
Browser  →  Next.js pages  →  API routes  →  MySQL  (workflow data)
                                          →  Neo4j  (complaint content graph)
```

* **MySQL** stores structured, consistency-critical data: users, roles, categories, and each complaint's status and assignment.
* **Neo4j** stores the content of each report as a graph of Complaint, Category and Location nodes.

One complaint exists in both databases. They are linked by `complaints.graph\\\\\\\_ref\\\\\\\_id` in MySQL, which equals the `refId` of the Complaint node in Neo4j. Since two different database systems cannot enforce a foreign key between them, the application keeps the link consistent (see Section 11).

## 8\. Database Choice and Justification

The data falls into two kinds, and each is stored where it is handled best.

**MySQL (relational) for workflow data.** Who filed what, the current status and who is assigned must stay consistent. That needs foreign keys, a CHECK constraint on status, and atomic updates, all of which MySQL provides.

**Neo4j (graph) for complaint content.**

* Complaints are naturally connected to categories and locations, and the lost/found matching is a relationship question: a lost report and a found report that share a Location node are linked through it.
* Node properties are schema-optional. A maintenance complaint carries `roomNumber` and `issueType`, and a lost-item report does not, so there are no empty columns and no migration when a category gains fields.
* Neo4j has a full-text index, which gives ranked text search over descriptions.

**Trade-off.** The two databases cannot share a transaction or a foreign key, so cross-database consistency is handled in the application (Section 11).

## 9\. NoSQL Data Model (Neo4j)

Nodes: `Complaint` (refId, mysqlId, description, isAnonymous, createdAt, and optional roomNumber and issueType), `Category` (name) and `Location` (name).
Relationships: `(Complaint)-\\\\\\\[:IN\\\\\\\_CATEGORY]->(Category)` and `(Complaint)-\\\\\\\[:AT\\\\\\\_LOCATION]->(Location)`.
Constraints and indexes: uniqueness on `Complaint.refId`, `Category.name` and `Location.name`, plus the full-text index `complaint\\\\\\\_text` on `Complaint.description`. The setup script is `neo4j/setup.cypher`.

**Anonymity by design.** Neo4j never stores who filed a complaint. The filer exists only in MySQL (`filed\\\\\\\_by`), which is NULL for anonymous complaints. An anonymous report therefore carries no identity in either database.

Full detail is in `docs/data-dictionary.md`.

## 10\. Important Queries

**List complaints (MySQL join):**

```sql
SELECT c.id, c.graph\\\\\\\_ref\\\\\\\_id, c.status, c.is\\\\\\\_anonymous, c.created\\\\\\\_at,
       cc.name AS category, c.filed\\\\\\\_by, c.assigned\\\\\\\_to
FROM complaints c
JOIN complaint\\\\\\\_categories cc ON c.category\\\\\\\_id = cc.id
ORDER BY c.created\\\\\\\_at DESC;
```

**Open complaints per category (view):**

```sql
SELECT \\\\\\\* FROM open\\\\\\\_complaints\\\\\\\_summary;
```

**Status update inside a transaction (MySQL):**

```sql
START TRANSACTION;
UPDATE complaints SET status = ?, assigned\\\\\\\_to = ? WHERE id = ?;
SELECT id FROM complaints WHERE id = ?;
COMMIT;   -- ROLLBACK if anything fails
```

**Create a complaint in the graph (Cypher):**

```cypher
MATCH (cat:Category {name: $category})
CREATE (c:Complaint)
SET c += $props, c.createdAt = datetime()
CREATE (c)-\\\\\\\[:IN\\\\\\\_CATEGORY]->(cat)
WITH c
FOREACH (\\\\\\\_ IN CASE WHEN $locationName IS NULL THEN \\\\\\\[] ELSE \\\\\\\[1] END |
  MERGE (l:Location {name: $locationName})
  CREATE (c)-\\\\\\\[:AT\\\\\\\_LOCATION]->(l))
RETURN c.refId AS refId
```

**Lost/found matching (Cypher):**

```cypher
MATCH (src:Complaint {refId: $refId})
OPTIONAL MATCH (src)-\\\\\\\[:AT\\\\\\\_LOCATION]->(srcLoc:Location)
CALL db.index.fulltext.queryNodes('complaint\\\\\\\_text', $searchText) YIELD node, score
WHERE node <> src
MATCH (node)-\\\\\\\[:IN\\\\\\\_CATEGORY]->(:Category {name: $oppositeCategory})
OPTIONAL MATCH (node)-\\\\\\\[:AT\\\\\\\_LOCATION]->(l:Location)
WITH node, score, l, coalesce(l = srcLoc, false) AS sameLocation
RETURN node.mysqlId AS id, node.description AS description,
       l.name AS location, sameLocation,
       score + CASE WHEN sameLocation THEN 1.0 ELSE 0.0 END AS finalScore
ORDER BY finalScore DESC
LIMIT 5
```

**Stored procedure and function (MySQL):**

```sql
SELECT days\\\\\\\_open(1);
CALL assign\\\\\\\_complaint(1, 2);   -- only an admin can be assigned
```

**CTE (resolution rate per category):**

```sql
WITH category\\\\\\\_stats AS (
  SELECT category\\\\\\\_id, COUNT(\\\\\\\*) AS total,
         SUM(status IN ('resolved','closed')) AS resolved
  FROM complaints GROUP BY category\\\\\\\_id
)
SELECT cc.name AS category, s.total, s.resolved,
       ROUND(100 \\\\\\\* s.resolved / s.total, 1) AS resolution\\\\\\\_pct
FROM category\\\\\\\_stats s JOIN complaint\\\\\\\_categories cc ON cc.id = s.category\\\\\\\_id
ORDER BY resolution\\\\\\\_pct DESC;
```

**Recursive CTE (complaints filed per day, last 7 days):**

```sql
WITH RECURSIVE days AS (
  SELECT CURDATE() - INTERVAL 6 DAY AS d
  UNION ALL
  SELECT d + INTERVAL 1 DAY FROM days WHERE d < CURDATE()
)
SELECT days.d AS day, COUNT(c.id) AS complaints\\\\\\\_filed
FROM days LEFT JOIN complaints c ON DATE(c.created\\\\\\\_at) = days.d
GROUP BY days.d ORDER BY days.d;
```

**Nested query (users who filed more than the average):**

```sql
SELECT u.name, u.email FROM users u
WHERE (SELECT COUNT(\\\\\\\*) FROM complaints c WHERE c.filed\\\\\\\_by = u.id) >
      (SELECT AVG(cnt) FROM (SELECT COUNT(\\\\\\\*) AS cnt FROM complaints
                             WHERE filed\\\\\\\_by IS NOT NULL GROUP BY filed\\\\\\\_by) t);
```

**Correlated query (open longer than the average for its category):**

```sql
SELECT c.id, c.status, days\\\\\\\_open(c.id) AS days\\\\\\\_open
FROM complaints c
WHERE c.status IN ('open','assigned','in\\\\\\\_progress')
  AND DATEDIFF(NOW(), c.created\\\\\\\_at) >
      (SELECT AVG(DATEDIFF(NOW(), c2.created\\\\\\\_at))
       FROM complaints c2 WHERE c2.category\\\\\\\_id = c.category\\\\\\\_id);
```

**Multi-table join:**

```sql
SELECT c.id, cc.name AS category, c.status,
       filer.name AS filed\\\\\\\_by, admin\\\\\\\_u.name AS assigned\\\\\\\_admin
FROM complaints c
JOIN complaint\\\\\\\_categories cc ON cc.id = c.category\\\\\\\_id
LEFT JOIN users filer   ON filer.id   = c.filed\\\\\\\_by
LEFT JOIN users admin\\\\\\\_u ON admin\\\\\\\_u.id = c.assigned\\\\\\\_to;
```

**Update and delete a complaint (Cypher and SQL):**

```cypher
MATCH (c:Complaint {refId: $refId}) SET c += $props
MATCH (c:Complaint {refId: $refId}) DETACH DELETE c
```

```sql
DELETE FROM complaints WHERE id = ?;
```

## 11\. Advanced Database Features

1. **Transactions (MySQL).** A status or assignment update runs inside `BEGIN` / `COMMIT` / `ROLLBACK`, so it applies completely or not at all.
2. **Trigger (MySQL).** `trg\\\\\\\_update\\\\\\\_last\\\\\\\_updated` sets `last\\\\\\\_updated` on every update, without any application code.
3. **View (MySQL).** `open\\\\\\\_complaints\\\\\\\_summary` provides an always-current count of open complaints per category for the admin dashboard.
4. **Full-text search with graph traversal (Neo4j).** The lost/found matching combines a full-text index over descriptions with a score bonus for reports that share a Location node.
5. **Indexing and constraints.** MySQL indexes on status, category, filer, assignee and creation time; unique graph references; foreign keys and CHECK constraints. Neo4j uniqueness constraints on `refId` and on category and location names, plus the full-text index.
6. **Stored procedure (MySQL).** `assign\\\\\\\_complaint(complaint\\\\\\\_id, admin\\\\\\\_id)` checks that the assignee has the admin role, then sets the status to `assigned`. It raises an error otherwise.
7. **Stored function (MySQL).** `days\\\\\\\_open(complaint\\\\\\\_id)` returns how many days a complaint has been open.
8. **CTE and recursive CTE (MySQL).** A CTE computes the resolution rate per category. A recursive CTE builds a 7-day calendar to count complaints per day.
9. **Nested and correlated queries (MySQL).** A nested query finds users who filed more complaints than average. A correlated query finds complaints open longer than the average for their own category.
10. **Create, read, update and delete in Neo4j.** Students can edit a complaint's description and location (the Neo4j node is updated and the Location relationship is re-linked) and delete a complaint (MySQL row and Neo4j node are both removed). Only the owner or an admin may do this.
11. **Role-based access in the database.** `database\\\\\\\_rbac.sql` defines `student\\\\\\\_role` and `admin\\\\\\\_role`, grants different table privileges, assigns each role to a separate MySQL test account, and sets the default role. Run it as a MySQL administrator. The app-level `appuser` remains a service account; per-student row ownership is enforced in the authenticated API, because MySQL table grants do not provide row-level filtering.
12. **Cross-database consistency (application level).** MySQL and Neo4j cannot share a transaction, so filing a complaint creates the Neo4j node first and then the MySQL row. If the MySQL insert fails, the node is deleted again (a compensating rollback). This was tested (test case 3).

## 12\. Authentication and Authorization

* Sign-up and login use NextAuth (Credentials provider) with JWT sessions. Passwords are hashed with bcrypt.
* Two roles, Student and Admin, stored in MySQL and carried in the session.
* **Page level:** middleware requires login for `/dashboard`, `/file-complaint` and `/my-complaints`, and restricts `/admin` to admins. Non-admins attempting `/admin` are redirected to `/dashboard` (test cases 9, 10 and 30).
* **API level:** every complaint and admin route reads the caller from the session (`lib/authz.ts`). Logged-out requests get 401. The admin routes (summary, status update, matching) return 403 to students, and students can only list and open their own complaints (test cases 18 to 22). The filer's identity is taken from the session, not from the request body.
* **Admin sign-up** requires an access code held in the `ADMIN\\\\\\\_SIGNUP\\\\\\\_CODE` environment variable, so choosing "Admin" in the form is not enough to create an admin account (test cases 23 and 24).
* Admins keep access to the student features by design, since an administrator may also want to file a report.

## 13\. Security and Data Integrity

* Passwords are stored only as bcrypt hashes.
* Database settings and secrets are read from environment variables. `.env.local` is excluded from Git, and `.env.example` holds placeholders. The passwords in `docker-compose.yml` are local development values.
* All SQL uses parameterized queries.
* Integrity is enforced in the databases: foreign keys, a CHECK constraint on status, unique emails in MySQL, and uniqueness constraints in Neo4j (test cases 5 to 8).
* The admin access code is also read from an environment variable and is never committed.
